자동화 개발자 면접 준비

사내 업무 자동화 개발자(Playwright · n8n · Airflow · Node.js/Python) 공고에 맞춘 준비 노트. 문제집으로 개념을 익히고, 여기서 과제와 면접 답을 준비한다. 빨간 글씨는 내 경험과 숫자로 직접 채워야 하는 곳.

공고 읽기전형별 준비과제 연습내 경험 꺼내기예상 질문역질문2주 계획

공고 읽기

이 자리는 "개발을 잘하는 사람"보다 다른 부서의 반복 업무를 이해하고, 굴러가는 자동화로 만들어 주는 사람을 찾는다. 공고의 문장마다 준비할 것이 있다.

전형별 준비

서류 → 과제 → 인터뷰(1, 2차) → 레퍼런스 체크 → 처우 협의 → 최종 합격. 수습 3개월 평가가 있다.

1. 서류 (국문 이력서 · 경력기술서)

  • 경력기술서 맨 위에 자동화와 닿는 일부터 쓴다. 직무 이름이 달라도 "반복 작업을 줄인 일", "배포·점검을 스크립트로 바꾼 일"은 모두 해당한다.
  • 한 줄마다 무엇을 → 어떻게 → 결과(숫자). 예: "수동 배포(약 10분)를 자동 배포로 바꿔 push 후 사람 손 0분".
  • 사이드 프로젝트는 주소와 저장소 링크를 넣는다. 공고가 우대 사항으로 직접 적었다.

2. 과제 전형

  • 아마 "어떤 사이트/API에서 데이터를 모아 정리하고 알리는" 작은 자동화일 가능성이 높다. 아래 과제 연습 3개를 미리 해 두면 뼈대를 그대로 쓴다.
  • 채점은 "돌아가는가"만이 아니라 실패 처리 · 재실행 · 설정 분리 · README를 본다. 기능을 더하기보다 이 네 가지를 먼저 채운다.

3. 인터뷰 (1차 실무 · 2차)

  • 1차는 과제 설명과 기술 질문, 2차는 일하는 방식·조직 적응이 중심일 것으로 본다. 과제의 모든 줄을 "왜 이렇게 했는지" 말할 수 있어야 한다.
  • 면접이 녹음·녹화될 수 있다고 공고에 적혀 있다. 놀라지 않게 알고 간다.

4. 레퍼런스 체크

  • 전 직장 동료·상사에게 확인 전화가 간다. 부탁할 사람 2명을 미리 정하고 양해를 구해 둔다. 면접에서 한 말과 어긋나지 않게 경력을 부풀리지 않는다.

과제 연습

직접 만들어 저장소에 올려 두면 과제 대비이자 포트폴리오가 된다. 쉬운 것부터.

연습 1 · 매일 아침 리포트 (크롤링/API → 저장 → 알림)

공개 API나 연습용 사이트에서 목록을 가져와, 날짜별로 파일(또는 SQLite)에 저장하고, 요약 한 줄을 슬랙(웹훅) 또는 텔레그램으로 보낸다.

  • 페이지를 끝까지 넘긴다. 가져온 건수를 로그에 남긴다.
  • 같은 날 두 번 돌려도 중복이 안 생긴다(날짜를 열쇠로 덮어쓰기).
  • 0건이면 실패로 처리하고 알린다.
  • 429·500번대는 간격을 늘려 다시 시도한다.
연습 2 · Playwright 로 로그인 → 조회 → 파일 내려받기

로그인이 필요한 연습용 사이트에서 로그인하고, 조건을 넣어 조회한 뒤, 표를 읽거나 파일을 내려받아 저장한다.

  • 로케이터는 getByRole · getByLabel 로. waitForTimeout 은 쓰지 않는다.
  • 로그인 상태를 storageState 로 저장해 재사용하고, 만료되면 다시 로그인한다.
  • 실패하면 스크린샷을 남기고 에러를 다시 던진다.
  • 계정은 .env 에. .gitignore 확인.
연습 3 · n8n 워크플로 (웹훅 → 가공 → 시트 → 알림 + 에러 워크플로)

n8n 을 내 컴퓨터에 띄우고(npx n8n), 폼/웹훅으로 들어온 요청을 정리해 구글 시트에 쌓고 알림을 보낸다.

  • Error Trigger 로 시작하는 에러 워크플로를 따로 만들어 연결한다.
  • 같은 일을 Airflow DAG 라면 어떻게 나눌지(작업 3개와 순서) 말로 설명할 수 있게 한다.
  • 워크플로를 JSON 으로 내보내 저장소에 올린다(버전 관리).

제출 전 확인

내 경험 꺼내기

자동화 직무 경력이 없어도, 이미 만든 것 안에 공고가 찾는 것이 들어 있다. 이 학습지 사이트가 그대로 재료다.

내가 만든 것공고의 말로 바꾸면
main 에 push 하면 서버가 1분마다 확인해 받아서 다시 빌드하는 자동 배포. 빌드가 실패하면 기존 버전이 그대로 돈다.반복 작업(배포) 자동화 + 예외 처리(실패해도 서비스 유지) + 실행 기록(로그 파일)
문제 데이터를 전부 검사하고 실행 예시를 서버에서 돌려 보는 점검 스크립트. 오류가 하나라도 있으면 올리지 않는다.결과 검증 단계 — 조용한 실패를 막는 장치
텔레그램으로 "문제 추가해 줘"라고 하면 AI 에이전트가 고치고, 점검하고, 올리면 자동 배포되는 흐름. 봇 계정에는 서버 관리 권한이 없다.메신저 트리거 → 작업 → 검증 → 배포로 이어지는 워크플로, 권한 분리, 바이브 코딩으로 MVP
기획 → 구현 → 배포 → 실제로 매일 사용하며 개선"작은 기능이라도 개선을 반복하며 완성도를 높이는" 경험, side project

직접 채우기: ① 전 직장에서 손으로 반복하던 일을 줄인 사례 1~2개 ② 그 일이 전에는 몇 분 걸렸고 지금은 몇 분인지 ③ 비개발 부서의 요청을 받아 만든 것 ④ 실패했던 자동화와 그때 고친 것

말하는 틀 (상황 → 과제 → 행동 → 결과)

"상황: 문제를 추가할 때마다 서버에 들어가 손으로 받아 빌드했습니다. 과제: 휴대폰에서도 문제를 고치고 바로 반영되게 하고 싶었습니다. 행동: 서버가 주기적으로 저장소를 확인해 새 커밋이 있으면 빌드하도록 만들고, 빌드가 실패하면 기존 버전이 그대로 돌게 했습니다. 올리기 전에는 점검 스크립트가 데이터 오류를 막습니다. 결과: 배포에 드는 손이 ○분 → 0분이 됐고, 잘못된 데이터가 올라간 적이 ○번 → 0번입니다."

C# 경력은 버리는 것이 아니다. "서버·DB·배포를 아는 사람이 자동화를 만들면 운영까지 책임질 수 있다"로 잇는다.

예상 질문

눌러서 펼친다. "왜 묻나"를 먼저 읽고, 답의 뼈대에 내 사례를 넣어 소리 내어 말해 본다.

지원 동기 · 경험

왜 자동화 개발자에 지원했나요? (C# 개발을 하다가 왜?)

왜 묻나: 서비스 개발 자리가 안 돼서 온 것인지, 이 일을 좋아하는지.

뼈대: ① 반복되는 일을 줄였을 때 가장 보람을 느꼈던 구체적 장면 → ② 그 뒤로 스스로 자동화한 것들(이 사이트의 배포·점검·봇) → ③ 그래서 한 제품의 기능보다 여러 부서의 문제를 푸는 일을 하고 싶다.

"코드를 짜는 것보다 문제를 해결하는 데 흥미"를 보여 주는 내 장면 하나를 정해 둔다.

가장 기억에 남는 자동화 경험을 말해 주세요.

왜 묻나: 실제로 해 봤는지, 결과를 숫자로 아는지, 실패를 겪어 봤는지.

뼈대: 상황 → 과제 → 행동 → 결과(시간·건수). 꼭 "처음에는 이렇게 실패했고 그래서 이렇게 고쳤다"를 넣는다. 실패 이야기가 있어야 직접 운영해 본 사람으로 들린다.

바이브 코딩(AI 도구)을 어떻게 쓰나요?

왜 묻나: 빨리 만드는 능력과, AI 가 만든 것을 검증하는 책임감.

뼈대: ① 무엇을 만들지와 규칙은 내가 정한다(이 저장소의 규칙 문서) ② AI 가 고친 것은 점검 스크립트를 통과해야 올라간다 ③ 서버 코드처럼 위험한 곳은 직접 확인한다 ④ 그래서 혼자서도 기획부터 배포까지 빠르게 MVP 를 낸다.

피할 말: "AI 가 다 해 줘요." 내가 설명 못 하는 코드는 내 것이 아니다.

기술

Playwright 자동화가 가끔 실패합니다. 어떻게 원인을 찾고 고치나요?

왜 묻나: 실제로 겪어 본 사람만 아는 답이 있다.

뼈대: ① 증거부터 — 실패 순간 스크린샷, 로그, trace ② 흔한 원인 순서로 확인 — await 누락, 고정 시간 대기, 깨지기 쉬운 로케이터, 로그인 만료, 팝업·점검 공지 ③ 고치기 — 조건을 기다리도록, 역할·라벨 로케이터로, 로그인 상태 재사용 + 만료 시 재로그인 ④ 재발 방지 — 실패 알림과 재시도.

Playwright 와 Selenium 의 차이는?

Playwright 는 요소가 준비될 때까지 스스로 기다려서(자동 대기) 불안정한 실패가 적고, 브라우저를 함께 설치해 주어 환경 맞추기가 쉽다. 네트워크 가로채기, trace, 로그인 상태 저장이 기본으로 있다. Selenium 은 역사가 길어 자료와 지원 언어가 많고 오래된 시스템에서 많이 쓴다. 새로 만든다면 Playwright 를 고르겠다. Selenium 을 써 본 적이 없다면 "써 보진 않았고 차이는 이렇게 이해한다"고 말한다.

크롤링할 때 주의할 점은?

① 공식 API 가 있는지 먼저 확인 ② robots.txt 와 이용 약관, 개인정보 ③ 요청 간격을 두어 상대 서버에 부담을 주지 않기 ④ 화면이 바뀌면 깨지므로 결과 검증(0건·빈 값)과 알림 ⑤ 로그인 정보는 환경 변수로.

n8n 과 Airflow 는 언제 무엇을 쓰나요?

여러 서비스를 잇는 가벼운 흐름과 즉시 반응(웹훅)은 n8n, 작업이 많고 순서·의존 관계·지난 날짜 재실행이 중요한 정기 데이터 작업은 Airflow, 스크립트 하나를 시간 맞춰 돌리면 cron 으로 충분하다. 써 본 범위를 솔직하게: "n8n 은 ○○ 를 만들어 봤고, Airflow 는 DAG 를 따라 만들어 본 수준입니다."

API 가 실패하면 어떻게 처리하나요?

응답 코드로 나눈다. 429·500번대는 간격을 늘려 몇 번 다시 시도, 401·403·404 는 다시 해도 소용없으니 바로 실패 처리하고 알린다. timeout 을 꼭 넣는다. 다시 시도해도 안전하도록 쓰기 작업은 열쇠 기준으로 덮어쓴다(멱등).

비밀번호나 API 키는 어떻게 관리하나요?

코드에 적지 않고 환경 변수나 도구의 비밀 저장소(n8n Credentials, Airflow Connections)에 둔다. .env 는 .gitignore. 실수로 올렸다면 지우는 것으로 끝이 아니라 키를 새로 발급받는다. 자동화 계정은 필요한 권한만 준다.

Node.js 와 Python 중 무엇이 더 편한가요? 다른 쪽은?

뼈대: 더 익숙한 쪽을 분명히 말하고, 다른 쪽은 "읽고 고칠 수 있고, ○○ 를 만들어 봤다"까지. 언어보다 HTTP·비동기·예외 처리 같은 공통 개념이 중요하다는 점, C# 경험이 타입과 구조에 도움이 된다는 점을 붙인다.

설계 · 상황

마케팅팀이 "매일 광고 성과를 엑셀로 정리하는 일을 자동화해 주세요"라고 합니다. 어떻게 진행하나요?

왜 묻나: 이 직무의 실제 하루. 순서대로 생각하는지 본다.

  1. 지금 어떻게 하는지 직접 본다. 왜 하는지, 결과를 누가 쓰는지 묻는다.
  2. 횟수 × 시간으로 효과를 잰다(지금 걸리는 시간을 기록).
  3. 데이터를 얻는 길을 고른다: 광고 플랫폼 API → 없으면 화면 자동화.
  4. 가장 작은 것부터 만든다: 숫자 한 줄을 슬랙에. 써 보게 하고 고친다.
  5. 실패 알림, 재시도, 결과 검증, README 를 붙인다.
  6. 한 달 뒤 절감 시간과 성공률을 숫자로 공유한다.
자동화가 조용히 틀린 데이터를 쌓고 있었다면?

① 먼저 멈추고 영향을 받는 사람에게 알린다 ② 언제부터 틀렸는지 범위를 찾는다 ③ 데이터를 바로잡는다(다시 돌려도 안전하게 만들어 뒀다면 그 기간을 재실행) ④ 원인을 고친다 ⑤ 같은 일이 다시 나면 바로 알도록 검증을 추가한다 ⑥ 무슨 일이 있었고 무엇을 바꿨는지 짧게 문서로 공유한다. 숨기지 않는 것이 핵심이다.

자동화 요청이 한꺼번에 5개 들어왔습니다. 무엇부터 하나요?

절감 시간(횟수 × 1회 시간), 규칙이 분명한가, 틀렸을 때의 위험, 만드는 데 드는 시간으로 견준다. 효과가 크고 빨리 되는 것부터. 순서를 혼자 정하지 않고 표로 만들어 요청자들과 공유한다.

자동화의 성과는 어떻게 측정하나요?

절감 시간, 처리 건수, 성공률, 요청부터 결과까지 걸리는 시간, 오류 건수. 만들기 전에 지금 수치를 재 둔다. 사람들이 실제로 쓰는지도 본다. 안 쓰는 자동화는 성과가 0이다.

협업 · 태도

개발을 모르는 동료에게 기술적인 내용을 어떻게 설명하나요?

그 사람의 업무 말로 바꾼다("API" 대신 "그 사이트가 숫자를 직접 건네주는 창구"). 되는 것과 안 되는 것, 언제 되는지를 먼저 말한다. 화면이나 예시 결과를 먼저 보여 준다. 실제로 그렇게 설명했던 일 하나.

문서화는 어떻게 하나요?

자동화마다 README 한 장: 무슨 일을, 어디서, 언제 도는지 / 설정 / 실패하면 무엇을 보는지 / 다시 돌리는 법. 바꾼 이유는 PR 과 커밋 메시지에. 이 저장소의 README 와 규칙 문서를 예로 보여 줄 수 있다.

이전 면접에서 떨어진 경험, 또는 본인의 부족한 점은?

뼈대: 사실 하나 → 그래서 무엇을 했는지 → 지금 달라진 점. 예: 부족한 기초를 메우려고 문제집을 직접 만들어 매일 풀고 있다는 것은 그대로 "개선을 반복하는 사람"의 증거다. 남 탓이나 변명으로 들리지 않게 짧게.

유연근무와 코어 타임, 빠르게 움직이는 조직에서 어떻게 일하나요?

작게 만들어 빨리 보여 주고 고치는 방식을 좋아한다는 것, 진행 상황을 먼저 공유한다는 것(슬랙·Jira), 막히면 오래 붙잡지 않고 묻는다는 것을 사례와 함께.
